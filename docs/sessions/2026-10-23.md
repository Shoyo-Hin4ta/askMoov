## Presenter and renderer agreed on nothing: the chart step is now one recorded decision

The positional rule had been tuned for the Gym case (a confirmation step appended after the answer) and broke as soon as the extra step came first. It cannot distinguish two rows-shaped steps at all.

**The change.** `VizSpec` gains `step`, the id of the plan step the chart is drawn from.
- The presenter names it. The present node lists every `answer_from` candidate with the chart type code derives from its shape, its row count and its columns (`<answer_steps>`), replacing the single `<viz_type>` suggestion. The output schema is built per run (`presentationFor(answer_from)`) with `step` as an enum of those ids.
- Code checks it. `vizMismatch`: for any chart type but `stat`, `x.field` and `y.field` must be columns of the chosen step, and a calc step (no rows) cannot be drawn as a table or chart. A miss, or a schema miss such as a step id outside the list, gets one corrective call with the problem spelled out (same pattern as the planner), then `VizValidationError` fails the run rather than shipping a mislabeled chart. `series` is not checked: stored runs show the presenter writes display labels there ("Tardies", "Scheduled days"), not column names. A `stat` tile uses no fields, and the presenter fills `x`/`y` on stat answers habitually, so stat is exempt.
- Everyone reads it. The answer card renders `viz.step` (`chartStepId`); the episode writer takes its shape from the same step. `answerStepId` remains only as the fallback for runs stored before today, which the reopened-thread view can still load.
- Evals: optional `viz_metric` on a golden case asserts the charted step is the one with that metric; set on `admin-passes-period-wing` and `admin-gym-visits`, the two shapes that pulled the positional rule in opposite directions.

**Found while checking the SDK, not assumed.** `zodOutputFormat` (SDK 1.1.0, `lib/transform-json-schema.js`) strips `enum` from the schema it sends and writes the allowed values into the field description; the wrapper's own `safeParse` enforces them. The API docs list `enum` as supported; keeping it in the grammar would mean bypassing the helper with a hand-built JSON schema, which is not worth the extra surface for a four-value list.

## Liveness is a timer, not a side effect of progress (2026-10-23, later session)

**Why.** Ritik: the heartbeat should keep happening on the side, whatever the run is doing. Until now `heartbeat_at` was written only when something finished (a node, then also every model round), so liveness depended on every long operation having its own deadline. The margin was implicit: a 90 s model deadline against the cron's 2-minute stale threshold, and nothing would have said so had someone raised one without the other.

**The change.** `packages/agent/src/heartbeat.ts`: `startHeartbeat({ beat, intervalMs, budgetMs, startedAt, onWarn })` returns `stop`. A `setInterval` every `HEARTBEAT_INTERVAL_MS` (30 s, shared) calls `ops.heartbeat(run.id, run.attempt)`; one beat in flight at a time; a failed write is reported through `onWarn` (console.error, no data) and the next tick still beats. Two self-stops: at `RUN_TIME_BUDGET_MS`, so a worker that is alive but stuck on an await falls silent and the cron rescues the run instead of believing it forever; and when a beat reports `lost`. `executeRun` starts it before the graph and clears it in `finally`. `ops.heartbeat` is now the lease renewal only: `UPDATE ... SET heartbeat_at = now() WHERE id = $1 AND status = 'running' AND attempt = $2`, returning `renewed` or `lost`, so a worker whose run the cron requeued and another invocation re-claimed cannot write over the new owner's beats. `ops.setCurrentNode` carries progress for the UI, written per node as before. The LLM wrapper's `onCall` is back to one job (the `llm_calls` row).

**Verified.** Five unit tests with fake timers (`heartbeat.test.ts`): beats on the interval and stops when told; stops at the budget (7 beats in 240 s at 30 s, none after); stops on `lost` with one warning; a failed write is reported and the next beat happens; a slow write is not stacked. 116 unit tests, typecheck clean. Live, one real run through `executeRun` with `heartbeatMs: 5_000` and a 1 s poller on the row (UTC): beats at 00:20:18.050, :23.050, :28.049, :33.049 while `current_node` moved sketch → plan → execute → critique on its own; after `succeeded` the row did not move for 12 s. Fence, directly: a fake running row on attempt 2 answers `lost` to attempt 1 and `renewed` to attempt 2 (the beat landed); after `status = succeeded` the owner gets `lost` too.

**Not changed.** The cron's 2-minute threshold and the 90 s per-call deadline. The deadline still bounds the work; it is no longer what keeps the run looking alive.

## Compiler casts, strict plan schemas, the deferred tests (2026-10-23, later session)
